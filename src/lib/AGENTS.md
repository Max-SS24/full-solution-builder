- Appointment-prep guidance is fixed VA.gov-sourced facts in src/lib/appointment-prep.ts; each is shown only after its allowlisted source page still contains its evidence phrases (prep_fact_checks, 1h cache, Sunday job), so stale or changed VA guidance is never presented as current.
- VA facility hours come from VA.gov ld+json openingHoursSpecification (formatHours in src/lib/va-hours.ts), refreshed in the Sunday VA batch and always shown with HOURS_NOTICE; community rows have no hours.
- Guidance reports are submitted only through a validated public server function using fixed fact IDs; admins review them, and reports never change fact verification.
- Signed-out guests get GUEST_DAILY_RESULTS result sets per rolling 24h (src/lib/guest-limit.ts), counted server-side via use_guest_result() on a hashed guest token plus a looser per-network cap; signed-in users are unlimited and crisis help is never counted.
- Guests never trigger paid AI: the chat uses the built-in guided extraction and provider matching uses basicMatch() (src/lib/basic-match.ts); only signed-in callers reach AI providers.
- Out-of-coverage places get the fixed note in src/lib/coverage.ts before the intake question; a U.S. state, territory or ZIP named in the same message always wins over the foreign-place list, and service history ("I served in Iraq") is never read as a location.
- Admins can deep-recheck failed weekly checks (src/lib/deep-check.server.ts: retries, HEAD→GET, content check); website results never change care status. Admins may also mark a failed row manually validated (history row only; never changes care status or dates); "Recheck all" loops batches until none remain.
- Website checks (weekly + deep) share homepage-check.ts rules: exact private-range IP blocking, same-site protocol hops allowed if the final page stays HTTPS, and 401/403/429-style firewall blocks reported as "blocked" (unconfirmed), never as down. Requests retry once with the honest CHECKER_HEADERS on dropped connections or 520/525/526 (network-side errors, not the site's answer), which stay unconfirmed — many hosts drop clients that fake a Chrome user agent. A 525/526 sets certificate "unverified" and that option is withheld from search, reopened and replacement results (care status unchanged); live search checks are saved to care_options.
- Manual validation changes use the admin/MFA-checked set_manual_validation RPC: row lock, state update and append-only history insert are atomic; identity and timestamps are server-derived, never client-supplied. History reads are admin-only and do not change listing evidence.
- Results show the latest Sunday check date (care_checked_at) separately from the last confirmed date (last_validated).

- Failed community_check_history rows auto-resolve via a care_options trigger (community_newer_pass) when a newer saved check (Sunday, deep or live search) passes every failed part; manual validation is separate.
- Certificate recoveries (cert unverified -> any other result on care_options.homepage_check) are logged by a DB trigger into certificate_recoveries; admins see and acknowledge them on /admin.
